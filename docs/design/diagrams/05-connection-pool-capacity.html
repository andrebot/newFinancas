Database Connection Pool Capacity

Every Resource Accessor call draws from one shared, fixed-size PostgreSQL connection pool — this is the real concurrency bottleneck for the system, not Node/Hono's request handling itself (event-loop based, not thread-per-request). Three scenarios below, each tied to a flow already documented elsewhere in this project, not invented for this diagram. Pool size shown as 10 throughout — illustrative, not yet a decided NFR; see the notes.

2. Delete User's cascade — the real design question this diagram surfaces

FR-1.17's cascade (docs/design/diagrams/sequences/identity-household/uc-12-delete-user.html) touches ~9 Accessors in sequence. The VBD doc's pipeline is written as numbered sequential steps, which settles order — it doesn't settle whether those 9 steps run inside one Postgres transaction or as 9 separate connection checkouts. Both are consistent with the VBD doc as written; they have opposite pool-occupancy shapes.

Option A — one atomic transaction. Data-integrity-safest (a half-completed GDPR delete would be a real compliance problem) — exclusive hold for the full cascade.

Given FR-1.17's GDPR stakes, Option A (one transaction) is the safer default — a half-completed erasure is a real compliance failure, not just a UX glitch — but it holds a connection roughly 9× longer than any other single request in this system, which is exactly the kind of thing worth knowing before, not after, a slow query inside that transaction ties up a slot under load.

Notes

  • Not a diagram type from harmonic-diagrams's original five (use-case activity, layered static architecture, call chain, component call-graph, sequence) — this is an infrastructure-capacity concern, not an architectural-decomposition one, hand-crafted with CSS Grid the same way layered static architecture diagrams are (precise banding mermaid's layout engine won't reliably guarantee).
  • Pool size 10 is illustrative, not a decided requirement — no NFR in this project specifies connection pool sizing yet. Same open-infrastructure-decision category as rate limiting, CORS, and queue/timeout behavior (see the callout above).
  • Node/Hono's own concurrency model is deliberately not shown as a bottleneck here — the event loop handles many concurrent requests without a thread per request; the pool above is the actual finite resource. A separate, smaller concern is Node's libuv thread pool (default size 4), relevant only where genuinely CPU-bound work gets offloaded off the event loop — in this system, that's specifically AuthenticationUtility's password hashing (Argon2/bcrypt) during register/login/change-password. Worth its own diagram only if/when that path is suspected to be a real bottleneck, not by default.
  • Every hold in scenarios 1 and 3 corresponds to exactly one Resource Accessor call from an already-documented sequence diagram — nothing here invents new request shapes.
