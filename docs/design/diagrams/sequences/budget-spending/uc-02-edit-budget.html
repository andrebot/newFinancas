Edit Budget

PATCH /households/:householdId/budgets/:budgetId — FR-4.9. Changing the target amount only affects the current and future Budget Periods; every past period keeps the target actually in effect at the time. The name, target and targets are written in one transaction (OQ-176).

sequenceDiagram
    actor User
    participant API as Hono route
    participant AM as AccountManager
    participant AU as AuthorizationUtility
    participant VU as ValidationUtility
    participant CA as CategoryAccessor
    participant UW as UnitOfWorkUtility
    participant BA as BudgetAccessor
    participant LOG as LoggingUtility

    User->>API: PATCH /households/:householdId/budgets/:budgetId {name?, targetAmount?, targets?: [...]}
    Note over API: no field for currency or visibility exists,
targetAmount ≥ 1, targets non-empty → else 422
    API->>AM: editBudget(context, householdId, budgetId, edit)
    AM->>BA: findById(householdId, budgetId)
    BA-->>AM: budget (or none)
    AM->>AU: authorize(actor, householdId, {data.edit, budget.visibility, budget.ownerUserId})
    alt not a member
        AM-->>API: 404 household.not_found
    else missing, or someone else's personal Budget
        AM-->>API: 404 budget.not_found
    else role may not edit (a Member may on a shared one they created)
        AM-->>API: 403 auth.forbidden
    else allowed
        AM->>VU: checkFields({name: nonBlank})
        alt blank name, or a target naming both ids or neither
            AM-->>API: 422 validation.failed {name, targets[i]}
        else targets sent
            AM->>CA: list(householdId)
            Note over AM,CA: a target the Budget already holds stays,
even once archived, a new one must be open
        end
        alt a new target archived or not this household's
            AM-->>API: 422 validation.failed {targets[i]...: field.invalid_option}
        else nothing sent
            AM-->>API: budget (read back, unaudited)
        else all checked
            AM->>UW: inTransaction(work)
            opt name or targetAmount sent
                AM->>BA: update(householdId, budgetId, {name, targetAmount}, this month)
                Note over BA: a new target writes this month's period (opened
if needed) and any later one — never a past one (FR-4.9)
            end
            opt targets sent
                AM->>BA: replaceTargets(householdId, budgetId, targets once each)
                Note over BA: dropped claims released, new ones claimed (OQ-166)
            end
            alt the Budget deleted meanwhile
                AM-->>API: 404 budget.not_found (rolled back)
            else a new target claimed elsewhere in the scope (FR-4.7)
                AM-->>API: 409 budget.target_already_claimed {target, budgetId} (rolled back)
            else a target gone since the check
                AM-->>API: 422 validation.failed (rolled back)
            else written
                UW-->>AM: committed
                AM-->>LOG: audit EditBudget
                AM->>BA: findById(householdId, budgetId)
                AM-->>API: budget
                API-->>User: 200 OK {budget}
            end
        end
    end
  • Historical actual-vs-target reporting never gets silently rewritten by a later edit — the immutable snapshot lives one layer down, not enforced here.
  • Corrected (OQ-176): update and replaceTargets used to be drawn as two separate writes, so a 409 on the targets left the new name and amount saved. They now share one transaction through UnitOfWorkUtility: a refusal keeps none of the edit.
  • See FR-4.7, FR-4.9, OQ-166, OQ-176.
