Reset Forgotten Password

Two-step flow — POST /auth/password-reset/request then POST /auth/password-reset/confirm — FR-1.13/OQ-115. The link works once, for 30 minutes; using it ends every session and lifts any login lock.

    actor User
    participant API as Hono route
    participant IM as IdentityManager
    participant UA as UserAccessor
    participant NE as NotificationEngine
    participant EA as EmailAccessor
    participant AN as AuthenticationUtility
    participant SA as SessionAccessor

    Note over User,API: Step 1 — request a reset token
    User->>API: POST /auth/password-reset/request {email}
    API->>IM: requestPasswordReset(email)
    IM-->>API: accepted (before any lookup)
    API-->>User: 202 Accepted
    Note over IM: the rest runs after the response, so neither the answer
nor its timing reveals whether the email has an account (OQ-115)
    IM->>UA: findByEmail(email)
    opt user exists
        UA-->>IM: found
        IM->>AN: issueOpaqueToken()
        AN-->>IM: {token, tokenHash}
        IM->>UA: storeResetToken(userId, tokenHash, expiresAt = now + 30 min)
        Note over UA: only the hash is stored (OQ-100)
        UA-->>IM: stored
        IM->>NE: notify("password.reset", recipient = {email, language}, params = {resetLink, expiresInMinutes: 30})
        Note over NE: resetLink = WEB_APP_URL + /reset-password?token=… —
routed to email, rendered in the recipient's language (OQ-113)
        NE->>EA: send({to, subject, body})
        Note over EA: only sends — provider = configuration (EMAIL_PROVIDER),
v1 console, terminal only (OQ-112)
        EA-->>NE: sent
        IM-->>LOG: log.info("Password reset link sent")
    end
    Note over IM: a failure here is logged (log.error), never returned

    Note over User,API: Step 2 — submit token + new password
    User->>API: POST /auth/password-reset/confirm {token, newPassword}
    API->>IM: confirmPasswordReset(token, newPassword)
    alt newPassword shorter than 12 characters
        Note over IM: checked first, so a too-short password
never uses up a valid link (OQ-103)
        IM-->>API: ValidationError
        API-->>User: 422 password.too_short {min: 12}
    else password long enough
    IM->>AN: hashOpaqueToken(token)
    AN-->>IM: tokenHash
    IM->>UA: consumeResetToken(tokenHash, now)
    Note over UA: atomic — unused and unexpired, then marked used:
the link works exactly once (FR-1.13)
    alt token invalid, expired or already used
        UA-->>IM: not consumed
        IM-->>API: BadRequest
        API-->>User: 400 password_reset.token_invalid
    else token consumed
        UA-->>IM: userId
        IM->>AN: hashPassword(newPassword)
        AN-->>IM: passwordHash
        IM->>UA: updatePasswordHash(userId, passwordHash)
        UA-->>IM: updated
        IM->>SA: deleteAllForUser(userId)
        Note over SA: every active session invalidated (FR-1.13) —
unlike Change Password, there is no "current session" to spare
        SA-->>IM: all sessions revoked
        IM->>UA: findById(userId), then clearLoginFailures(emailKey)
        Note over UA: resetting proves control of the email,
so any login lock on it is lifted (OQ-115)
        UA-->>IM: cleared
        IM-->>LOG: log.audit("ResetPassword", User userId)
        IM-->>API: reset
        API-->>User: 200 OK
    end
    end
  • One use case, two HTTP requests — shown as a single diagram since FR-1.13 describes them as one continuous flow, separated by however long the user takes to check their email.
  • Step 1 answers 202 before looking anything up (OQ-115): the branch runs after the response (opt, not alt), so neither the answer nor how long it took leaks account existence. A failure to send is logged, never returned.
  • Email is a channel the Engine chooses, not one the Manager asks for (OQ-113): the Manager supplies a recipient with an email and language because password.reset is routed to email — the type system rejects a recipient without them.
  • Contrast with Change Password (UC-19): a forgotten-password reset can't spare "the current session" (the user isn't logged in at all), so every session goes.
  • See FR-1.13.
