Login

POST /auth/login then POST /auth/mfa/verify — FR-1.2/OQ-30/OQ-114/OQ-145. Two steps: the password earns a five-minute challenge, the MFA code trades it for a session. The password step answers one 401 for every failure; both steps count against the same per-address lockout — whether or not an account exists.

  • Two steps (OQ-145). The single request (password + MFA code together) made a wrong code indistinguishable from a wrong password, so the user had to retype everything. Now the password step answers a five-minute challenge token and the code is retried alone, as in most apps.
  • Enumeration guard kept where it matters: the password step still answers auth.invalid_credentials for an unknown email and a wrong password alike, and a missing user still costs a password check. Step 2 names a wrong code (auth.mfa_invalid) — its caller already proved the password, so that reveals nothing new.
  • Lockout (OQ-114) spans both steps: 5 failures — wrong passwords and wrong codes alike — within 15 minutes lock the address for 15 minutes (config/constants.ts). Only a full sign-in clears the count; a correct password does not, or it could buy endless code guesses. The count lives in login_attempts, keyed by address, so an address with no account locks exactly like one with an account. The Manager decides; UserAccessor applies (atomic count, lock, clear).
  • The challenge token is stateless (a JWT naming the user and address): no table, and reusing it within its five minutes still needs a correct code, under the same lockout.
  • The access token is never persisted (OQ-30); only the refresh token is server-tracked in sessions.
  • Unconfirmed MFA enrollment (OQ-149): an account whose first authenticator code never arrived gets no challenge — the right password answers a fresh enrollment (new secret and recovery codes, replacing the ones no one saw), confirmed through UC-11b. The answer is tagged by step (mfa or enroll). A wrong password is answered as before, so this reveals nothing to someone without it.
