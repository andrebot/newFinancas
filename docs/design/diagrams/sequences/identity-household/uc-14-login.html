Login

POST /auth/login — FR-1.2/OQ-30/OQ-114. Password and MFA code together in one request. Every failure answers the same 401, and an address with too many failures is locked for a while — whether or not an account exists.

    actor User
    participant API as Hono route
    participant IM as IdentityManager
    participant UA as UserAccessor
    participant AN as AuthenticationUtility
    participant SA as SessionAccessor
    participant LOG as LoggingUtility

    User->>API: POST /auth/login {email, password, mfaCode}
    API->>IM: login(input, deviceInfo = User-Agent)
    IM->>UA: findLoginLock(emailKey)
    Note over UA: emailKey = trimmed, lower-cased email — login_attempts
is kept per address, not per account (OQ-114)
    UA-->>IM: lockedUntil (or none)
    alt address locked (lockedUntil > now)
        IM-->>API: TooManyRequests {retryAfterSeconds}
        API-->>User: 429 auth.too_many_attempts (Retry-After)
    else not locked
        IM->>UA: findByEmail(email)
        UA-->>IM: user with passwordHash, encryptedMfaSecret, systemRole (or none)
        IM->>AN: verifyPassword(passwordHash or a dummy hash, password)
        Note over IM: a missing user still costs one Argon2 check —
response time doesn't reveal whether the email exists
        AN-->>IM: valid / invalid
        opt user found and password valid
            IM->>AN: verifyTotp(encryptedMfaSecret, mfaCode)
            AN-->>IM: valid / invalid
        end
        alt any factor failed (no user, wrong password, wrong code)
            IM->>UA: recordLoginFailure(emailKey, now, windowStart = now − 15 min)
            Note over UA: atomic: failures older than the window are
forgotten, then this one is counted
            UA-->>IM: failuresInWindow
            opt failuresInWindow ≥ 5 (the Manager's rule)
                IM->>UA: lockLogin(emailKey, until = now + 15 min)
                UA-->>IM: locked
            end
            IM-->>API: Unauthorized
            API-->>User: 401 auth.invalid_credentials (same for every factor)
        else every factor valid
            IM->>UA: clearLoginFailures(emailKey)
            UA-->>IM: cleared
            IM->>AN: issueOpaqueToken()
            AN-->>IM: {token, tokenHash}
            IM->>SA: insert(userId, tokenHash, deviceInfo, expiresAt = now + 30 days, now)
            Note over SA: stores only the hash (OQ-100)
            SA-->>IM: session
            IM->>AN: signAccessToken({userId, sessionId, systemRole})
            Note over AN: sid tells the device apart (OQ-106), role is the system role (OQ-111)
            AN-->>IM: accessToken (15-minute JWT)
            IM-->>LOG: log.audit("Login", Session sessionId)
            IM-->>API: {accessToken, refreshToken}
            API-->>User: 200 OK {accessToken, refreshToken}
        end
    end
  • One 401 for every failure — unknown email, wrong password and wrong MFA code all answer auth.invalid_credentials, and a missing user still costs a password check, so neither the code nor the timing tells an attacker which factor failed or whether the email is registered. The earlier diagram showed auth.mfa_invalid for a wrong code; corrected.
  • Lockout (OQ-114): 5 failures within 15 minutes lock the address for 15 minutes (config/constants.ts); a success clears it. The count lives in login_attempts, keyed by address, so an address with no account locks exactly like one with an account — a 429 never confirms registration. The Manager decides (threshold, window, lock length); UserAccessor applies (atomic count, lock, clear) — the counter is a protection on the user's credentials, next to the hashes, MFA secret, recovery codes and reset tokens it already owns, so no new Accessor.
  • The access token is never persisted (OQ-30); only the refresh token is server-tracked in sessions.
  • See FR-1.2, OQ-30, OQ-100, OQ-106, OQ-111, OQ-114.
