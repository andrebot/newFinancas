Create User (Registration)

POST /auth/register — FR-1.1/FR-1.15. Every account enrolls TOTP-based MFA and receives recovery codes at registration, before it can be used to log in.

  • MFA enrollment is not optional or deferred — FR-1.15 requires it complete before the account can log in at all, so it happens inline in registration, not as a follow-up step.
  • Confirmed by its first code (OQ-149). The enrollment stays unconfirmed until POST /auth/mfa/enrollment/confirm (UC-11b) receives a code from the app, with the enrollmentToken answered here; that confirmation opens the first session. Signing in before then answers a fresh enrollment instead of a challenge (UC-14), so a user who closed the tab before scanning is never locked out.
  • otpauthUri carries the issuer and TOTP settings (config/constants.ts), so the web app draws the QR without repeating them.
  • The account starts in the language it registered in (OQ-161). The web app sends the locale it shows; without it the account is pt-BR. Otherwise the app would switch language once the user signs in and their saved preference applies.
  • The recovery codes are returned exactly once, at creation — the backend stores only their hashes (mfa_recovery_codes.code_hash), never the plaintext codes themselves after this response.
  • Redrawn to the implementation (M1): the route is POST /auth/register (was shown as POST /users); request shape is checked at the route against the contract, not by a ValidationUtility; a duplicate email is the insert's typed result, not a prior lookup that two simultaneous registrations could both pass.
  • See FR-1.1, FR-1.15, OQ-29 (first_name/last_name resolved during data modeling), OQ-114, OQ-116, OQ-149.
