Delete User (GDPR Right-to-Erasure)

DELETE /users/me — FR-1.17/FR-1.18/OQ-25/OQ-240. One of the two widest-fan-out flows in the system (the other is Record Transaction's investment-buy sub-case). Personal data is hard-deleted; shared data is anonymized, not deleted.

  • No rule refuses it (FR-1.17): a user can always delete their own account. The 409 and 500 are not refusals — a household that kept changing, and the database's safety net (02-data-model.md rule B) — and in both the next try finishes the job.
  • Departures first, then one erasure (OQ-240). Each departure commits on its own; the erasure and the user row go in one transaction (UnitOfWorkUtility), so the user's data is erased whole or not at all. The erasure runs everywhere, not per household: households the user left before task 136 shipped are covered too.
  • Trigger equivalence: the same erasure, scoped to one household, runs on Leave Household and Remove Member (UC-07/UC-08) — see the cross-cutting note at the top of docs/architecture/02-data-model.md.
  • Rebuilt (task 136): the design-time sequence called InvestmentHoldingAccessor and SessionAccessor.deleteAllForUser — both are FK cascades (Holdings with their personal Account, sessions with the user row).
  • Confirmed, not a gap: if a deleted user's personal Holding was funding a still-live shared Goal, that Goal survives and its progress simply recomputes from whatever Holdings remain — "the user removed their finances from the household."
  • audit_log_entries.actor_id is a plain value, not a foreign key — this row (and every other audit entry naming this actor) survives untouched; there is nothing to rewrite or purge (OQ-25/NFR-AUD-1).
