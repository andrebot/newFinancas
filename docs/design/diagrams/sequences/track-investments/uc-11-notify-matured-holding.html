Notify Matured Holding

System-triggered by investmentsDaily, no HTTP route — FR-5.8, FR-6.5/OQ-68/OQ-72.

sequenceDiagram
    participant CRON as investmentsDaily
    participant IHA as InvestmentHoldingAccessor
    participant SB as ServiceBusUtility
    participant AM as AccountManager
    participant HA as HouseholdAccessor
    participant NE as NotificationEngine
    participant NIA as NotificationInboxAccessor
    participant LOG as LoggingUtility

    CRON->>IHA: findMaturedWithPosition(today)
    Note over IHA: fixed-term, dueDate < today, quantity > 0,
not yet notified
    IHA-->>CRON: [{holdingId, accountId, householdId, ownerUserId, visibility, assetType, ticker, dueDate}, ...]
    loop for each matured Holding
        CRON->>SB: publish("holding.matured", {holdingId, householdId, ownerUserId, visibility, ...})
        SB-->>AM: subscribe("holding.matured")
        alt shared Account
            AM->>HA: listMembers(householdId)
            HA-->>AM: the members — each is a recipient (OQ-171)
        else personal Account
            Note over AM: the recipient is ownerUserId
        end
        loop for each recipient
            AM->>NE: notify("holding.matured", recipient = {userId}, params = {holdingId, holdingName, dueDate})
            Note over NE: routing table: holding.matured → in-app
            NE->>NIA: insert(userId, "holding.matured", params)
            NIA-->>NE: stored
            NE-->>AM: delivered
        end
        alt every owner notified
            AM->>IHA: markMaturedNotified(holdingId)
        else a delivery failed
            Note over AM: not marked — tomorrow's run tries again
        end
        AM-->>LOG: logActivity(correlationId, systemActor, "NotifyMaturedHolding")
    end
  • Type + params, never text (OQ-82): the frontend renders “CDB Banco Inter 2026 reached its due date… archive it?” in the user's language. holdingName is a deliberate snapshot (historical label).
  • Recipients are the Manager's (OQ-171): the Accessor returns the Holding's Account owner and visibility; a shared Account's recipients are its household's members, read through HouseholdAccessor — the Accessor never reads memberships.
  • Synchronous on purpose: unlike invitations, the Manager waits for NotificationEngine, because marking the Holding notified depends on it (BDT plan).
  • Normally a redemption (UC-4) zeroes and auto-archives the Holding first; this catches the rest.
  • See FR-5.8, FR-6.5, OQ-68, OQ-72, OQ-82; Manager review M6.
