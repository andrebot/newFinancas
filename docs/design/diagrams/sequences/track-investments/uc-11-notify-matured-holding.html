Notify Matured Holding

System-triggered by investmentsDaily, no HTTP route — FR-5.8, FR-6.5/OQ-68/OQ-72.

sequenceDiagram
    participant CRON as investmentsDaily
    participant IHA as InvestmentHoldingAccessor
    participant SB as ServiceBusUtility
    participant AM as AccountManager
    participant HA as HouseholdAccessor
    participant NE as NotificationEngine
    participant NIA as NotificationInboxAccessor
    participant LOG as LoggingUtility

    CRON->>IHA: findMaturedWithPosition(today)
    Note over IHA: fixed-term, redemption date < today, quantity > 0,
not archived, not yet notified
    IHA-->>CRON: [{holdingId, accountId, householdId, ownerUserId, visibility, assetType, ticker, dueDate}, ...]
    loop for each matured Holding
        CRON->>SB: publish("holding.matured", the row)
        SB-->>AM: subscribe("holding.matured") — notifyMaturedHolding, as the system
        alt shared Account
            AM->>HA: listMembers(householdId)
            HA-->>AM: the members — each is a recipient (OQ-171)
        else personal Account
            Note over AM: the recipient is ownerUserId (none if the owner is gone)
        end
        par for each recipient
            AM->>NE: notify("holding.matured", {userId}, {holdingId, assetType, ticker, dueDate})
            Note over NE: routing table: holding.matured → in-app
            NE->>NIA: insert(userId, "holding.matured", params)
            NIA-->>NE: stored
            NE-->>AM: delivered (or rejected)
        end
        alt every delivery succeeded
            AM->>IHA: markMaturedNotified(holdingId)
            AM-->>LOG: info "Matured holding notified" {holdingId, recipients}
        else a delivery failed
            AM-->>LOG: warn "not marked" {holdingId, recipients, failed}
            Note over AM: not marked — tomorrow's run tries again
        end
    end
  • Type + params, never text (OQ-82): the frontend renders “Your CDB matured on 2026-10-01. Archive it?” in the reader's language from assetType. OQ-178: the params carry assetType and ticker instead of a holdingName — a Holding has no name, and a label is the reader's language's to build.
  • Recipients are the Manager's (OQ-171): the event carries the Holding's Account owner and visibility; a shared Account's recipients are its household's members, read through HouseholdAccessor — the Accessor never reads memberships.
  • Synchronous on purpose: unlike invitations, the Manager waits for every delivery (all settled), because marking the Holding notified depends on them all. A partial failure re-notifies tomorrow, including those already told — accepted.
  • The publisher (investmentsDaily) is task N9; this subscription is built with M2 part 5.
  • Normally a redemption (UC-4) zeroes and auto-archives the Holding first; this catches the rest.
  • See FR-5.8, FR-6.5, OQ-68, OQ-72, OQ-82, OQ-171, OQ-178; Manager review M6.
