Delete Transaction

DELETE /households/:householdId/transactions/:transactionId — FR-3.2. Same reverse-effect complexity as Edit, without a reapply step.

    else a fixed-term buy whose schedule has posted
        TM-->>API: Conflict

    else the buy that created its Holding, and other transactions reference it
        TM->>ATA: countForHolding(holdingId, buyId)
        ATA-->>TM: n > 0
        TM-->>API: Conflict
        API-->>User: 409 transaction.holding_in_use {count} (OQ-201)

        AZ-->>TM: allowed

            TM->>AA: applyMovement(accountId, {-amount, currency, date})

            end
        else was an investment trade
            TM->>AA: applyMovement(accountId, {±amount reversed, currency, date})
            alt the buy that created its Holding, nothing else references it
                TM->>GA: replaceAllocations(householdId, holdingId, [])
                TM->>IHA: delete(holdingId)
                Note over IHA: the Holding goes with its buy — snapshots and schedule cascade (OQ-201)
            else
                TM->>IHA: applyTrade(holdingId, {-quantityDelta, -costBasisDelta})
                TM->>VSA: deleteAutomatic(transactionId)
                TM->>IHA: unarchiveIfSystemArchived(holdingId)

            end

            TM->>CCA: applyMovement(cardId, {-signedAmount, currency, date})
        end

        TM->>ATA: delete(transactionId, expected)
        alt the values read changed meanwhile
            ATA-->>TM: stale

            TM-->>API: Conflict

  • A deleted, backdated transaction runs the balance cascade in reverse across every subsequent month, same mechanic as Edit (UC-02) minus the reapply half.
  • OQ-201: a trade's cash leg is reversed too. Deleting the buy that created a Holding deletes the Holding (its Goal split, snapshots and schedule with it) when no other transaction references it, and is refused otherwise; a fixed-term buy whose schedule has posted can't be deleted. A deleted transaction the schedule posted isn't posted again — its entry stays marked.
