Delete Transaction

DELETE /households/:householdId/transactions/:transactionId — FR-3.2. Same reverse-effect complexity as Edit, without a reapply step.

    User->>API: DELETE /households/:householdId/transactions/:transactionId
    API->>TM: delete(actor, transactionId)
    TM->>ATA: findById(householdId, transactionId) (else the card ledger)
    ATA-->>TM: the stored transaction
    TM->>AZ: canWrite(actor, transactionId)? — on a shared Account its recorder's, on a personal one its owner's (OQ-223)
    alt not authorized
        AZ-->>TM: denied
        TM-->>API: Forbidden
        API-->>User: 403 auth.forbidden
    else its Account (a card row's: its card's) is archived — history is frozen (FR-2.4, OQ-220)
        TM-->>API: Conflict
        API-->>User: 409 account.archived
    else a bill payment whose card's Account the actor may no longer edit, or is archived (OQ-219)
        TM-->>API: NotFound or Conflict
        API-->>User: 404 credit_card.not_found or 409 credit_card.account_archived
    else a fixed-term buy whose schedule has posted
        TM-->>API: Conflict
        API-->>User: 409 transaction.schedule_started (OQ-201)
    else authorized
        AZ-->>TM: allowed
        alt was a balance movement or bill payment
            TM->>AA: applyMovement(accountId, {-amount, currency, date})
            opt was a bill payment
                TM->>CCA: applyMovement(cardId, {+amount, currency, date})
            end
        else was an investment trade
            TM->>AA: applyMovement(accountId, {±amount reversed, currency, date})
            TM->>IHA: applyTrade(holdingId, {-quantityDelta, -costBasisDelta})
            opt the undo reopens a zeroed position
                TM->>IHA: unarchiveIfSystemArchived(holdingId)
                Note over IHA: if this was the sell/redemption that zeroed the
Holding, it comes back (OQ-80) — user archives stay,
and its automatic snapshot dies with the row (OQ-56)
            end
        else was a card charge/refund
            TM->>CCA: applyMovement(cardId, {-signedAmount, currency, date})
        end
        TM->>BA: accrueIfClaimed({accountScope, currency, categoryId, subcategoryId, ∓amount, date})
        TM->>ATA: delete(transactionId, expected)
        alt the values read changed meanwhile
            ATA-->>TM: stale
            Note over TM: refuse — the unit of work rolls every reversal back (OQ-107)
            TM-->>API: Conflict
            API-->>User: 409 transaction.changed (reload and retry)
        else deleted
            opt was an investment trade whose undo zeros the position again
                TM->>ATA: countForHolding(holdingId, buyId)
                alt n = 0 — the buy that created its Holding
                    TM->>IHA: delete(holdingId)
                    Note over IHA: the row is gone first, so nothing still points
at it — the Goal split, snapshots and schedule cascade (OQ-201, OQ-56)
                else n > 0 and this buy created it
                    TM-->>API: Conflict
                    API-->>User: 409 transaction.holding_in_use {count} (OQ-201) — rolled back
                else a re-buy into an existing one
                    TM->>IHA: archive(holdingId, system)
                end
            end
            opt was the trade's split still current
                TM->>GA: deleteFrom + reopenClosedAt (the split comes back with the position)
            end
            TM-->>LOG: logActivity(correlationId, actor, "DeleteTransaction")
            TM-->>LOG: recordAudit(actor, "Transaction", transactionId)
            TM-->>API: deleted
            API-->>User: 204 No Content
        end
    end
  • PR #145 review: a trade's change restates its Holding's automatic snapshots from the whole history (listTrades, list, then updateAutomatic where a value or date moved), so later trades' values follow it; a pair's two sides are written in Account-id order.
  • OQ-222: deleting either side of a transfer between own accounts deletes both, moving both accounts back, in the same unit of work; the caller must be able to edit both accounts (403 otherwise).
  • A deleted, backdated transaction runs the balance cascade in reverse across every subsequent month, same mechanic as Edit (UC-02) minus the reapply half.
  • OQ-201: a trade's cash leg is reversed too. Deleting the buy that created a Holding deletes the Holding (its Goal split, snapshots and schedule with it) when no other transaction references it, and is refused otherwise; a fixed-term buy whose schedule has posted can't be deleted. A deleted transaction the schedule posted isn't posted again — its entry stays marked.
  • OQ-219: a bill payment's card may sit on another Account than its payer, so editing or deleting it decides on both: the card's Account must still be one the actor may edit (404 credit_card.not_found) and open (409 credit_card.account_archived).
