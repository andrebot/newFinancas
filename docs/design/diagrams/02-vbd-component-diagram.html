Backend VBD Decomposition

Managers / Engines / Resource Accessors / Utilities for the New Finance App backend, derived from docs/requirements/01-core-use-cases.md, 02-functional-requirements.md, and — as of Round 7 — docs/architecture/00-core-process-patterns.md's 4 core process patterns, which now supersede the CUC list as the primary decomposition input. Full component tables, the per-Manager call table, and the household-lifecycle/scheduled-trigger flows live in docs/architecture/backend/01-vbd-decomposition.md — this page is the rendered version of the two diagrams from that document.

Component Diagram

Revised seven times. Rounds 1–5: 18→4 Managers (grouped by trigger pattern, fractal, pub/sub-only between them), 14→9 Engines (removing dispatch tables and thin validate-then-write logic). Round 6: AccessControlEngine reclassified as a Utility; PortfolioBuilderEngine and OpenBankingSyncEngine removed (no real backend computation to isolate); HoldingValuationEngine, BudgetTrackingEngine, GoalProgressEngine, CreditCardBalanceEngine removed (each a workflow decision plus a validated write, not computation) → 1 Engine (ReportingEngine). Round 7 — driven by full use-case verification and volatility reconciliation, not a fresh guess: Engines → 2 (added InvestmentProductEngine for FR-11's instrument-specific maturity/interest/tax rules, called inline by TransactionManager — never by AccountManager). Resource Accessors: 17 active + 4 parked (removed CurrencyReferenceRateAccessor entirely — currency conversion turned out to be frontend-only, never persisted; split InvitationAccessor out of HouseholdAccessor; parked the Open Banking/analysis Accessors alongside their deferred CUCs, not dropped). Utilities: 7, down from 9 — merged ApplicationLogUtility + AuditLogUtility → LoggingUtility; split the old AccessControlUtility grouping into AuthenticationUtility (crypto primitives) and AuthorizationUtility (role/permission gate — a different volatility driver). Managers stay at 4 — the process-pattern axis is orthogonal to the trigger-pattern axis that already grouped them. Round 8 — closing three cascades the data-modeling pass surfaced, not a fresh design pass: Resource Accessors: 18 active, up from 17 (added RecurringTransactionScheduleAccessor, backing FR-3.5's recurring transactions — a fourth entry point into TransactionManager's pipeline, the same shape as Open Banking sync and the scheduled investment-cash-event trigger). FR-4.4's budget-alert threshold is removed (OQ-52) — no more NotificationDeliveryUtility edge from TransactionManager. Fixed-term instrument Holdings (OQ-50/51) now branch TransactionManager's Holding-create step and ReportingEngine's read path on assetType. Round 9 (this revision, Oct 2026 design round): "Objective" → "Goal"; RecurringTransactionScheduleAccessor removed (OQ-55); new IndexRateAccessor (FR-11.6); DashboardAccessor parked until v3; one daily investmentsDaily trigger for cash events + matured holdings; InvestmentProductEngine.project called by InsightsManager; NotificationDeliveryUtility wired again (invitations, matured holdings). Still 4 Managers, 2 Engines, 7 Utilities, 18 active Accessors.

Two Engines now — ReportingEngine under InsightsManager, InvestmentProductEngine under TransactionManager, called inline within the investment-buy path — and, since Round 9, by InsightsManager for project (expected payout/taxes). Two scheduled triggers — CRON_INV (Round 9: cash events + matured holdings in one daily job) is live; CRON_OB is parked alongside the four dashed Open-Banking/analysis Accessors it feeds. There is still no direct Manager↔Manager edge anywhere in this diagram — every Manager-to-Manager effect, including the new household.created → Category-seeding edge, routes through ServiceBusUtility, never one Manager calling another directly. Round 8: TransactionManager's fire-and-forget edge to NotificationDeliveryUtility is removed — the threshold-crossed signal it fired on is gone (FR-4.4 removed, OQ-52); the Utility stays in the diagram, just currently unwired from any Manager. ReportingEngine gains a new edge to InvestmentHoldingAccessor (OQ-51) — it now reads a fixed-term Holding's cost_basis directly, since those Holdings never populate a Valuation Snapshot.

Sequence Diagram — Record an Account Transaction (richest flow)

Redrawn, Round 7 — genuinely richer than before. Round 7 found an even denser variant than this diagram used to show: buying a new fixed-term instrument for the first time, the one path where InvestmentProductEngine actually appears. Every participant is TransactionManager itself, a Utility, or a Resource Accessor — except the Engine, called inline, once, only for that sub-case. Round 8: the Holding auto-create step now branches on assetType (OQ-50 — a fixed-term instrument always gets a new Holding, never matches by ticker) rather than testing "no existing Holding" alone; the Valuation Snapshot side effect is annotated as market-priced-only (OQ-51); and the threshold-crossed branch plus NotificationDeliveryUtility participant are removed entirely, since FR-4.4's alert threshold no longer exists (OQ-52).

    Note over TM: effect = EFFECT_BY_KIND[kind] — inline lookup (see doc §3.1)
    alt effect = simple movement / transfer / bill-payment debit
        TM->>AA: applyMovement(accountId, amount, currency)
        AA-->>TM: new balance (rejects on currency mismatch, FR-2.2)
    else effect = investment trade
        Note over TM: quantityDelta computed here (buy/sell/redemption rule)
        opt kind = investment buy
            alt assetType is one of FR-11.1's fixed-term instruments (e.g. CDB, Tesouro Direto)
                TM->>IHA: create a new Holding — always, never accumulates (OQ-50)
                IHA-->>TM: new holdingId
            else no existing Holding for this ticker+account
                TM->>IHA: create Holding (auto-create, FR-5.1/OQ-41)
                IHA-->>TM: new holdingId
            end
        end
        TM->>IHA: applyTrade(holdingId, quantityDelta, valuation, date)
        IHA-->>TM: updated Holding + Valuation Snapshot recorded (market-priced assetType only — OQ-51)
        opt assetType is a defined FR-11.1 instrument type (e.g. CDB, Tesouro Direto)

            IPE-->>TM: {maturityDate, interestDates[], taxRule}
            TM->>IHA: applySchedule(holdingId, schedule)
            IHA-->>TM: schedule stored
        end
    end
