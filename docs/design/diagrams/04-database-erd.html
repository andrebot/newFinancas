Database ERD

Every table confirmed in docs/architecture/02-data-model.md, grouped into the same 7 domains that document uses, in the order it presents them. Each panel is its own diagram rather than one giant interconnected graph — with 26 tables across the whole schema, one canvas would be unreadable. Where a table's full definition lives in another panel, it appears here as a two-attribute stub (just id and a pointer) purely so the relationship is visible in context — see the "How to read this" note below the diagrams for exactly what that means.

How to read this

Each panel is one domain from 02-data-model.md, in the same order. A table shown with just id PK and a ref line (e.g. households inside the Financial Accounts panel) is the same real table, not a copy — it's drawn minimally in a non-owning panel purely so the relationship line has somewhere to land. Its full column list only appears once, in the panel that owns it. Relationship cardinality follows the FK's actual nullability in the data model — a nullable FK (e.g. accounts.owner_user_id) is drawn zero-or-one on that side, not exactly-one.

Cross-domain relationships (consolidated)

This closes the "Not yet done" item in 02-data-model.md asking for a consolidated summary of which tables carry the nullable actor-reference-for-anonymization pattern (FR-1.17), rather than repeating the reasoning per table:

  • Dual-role nullable owner_user_id (identity for personal, provenance for shared, nulled on user deletion or leaving/removal from the household): accounts, budgets (and denormalized onto budget_targets), goals.
  • Never holds shared data, so no anonymization branch at all — always just cascade-deletes with its owner: dashboard_widgets, notifications, sessions, mfa_recovery_codes.
  • Pure household-shared taxonomy, no personal/shared split, so no actor reference to null in the first place: categories, subcategories.
  • Nullable FK for a different reason entirely — history preservation on a hard delete, not anonymization: budget_periods.budget_id (ON DELETE SET NULL when a Budget is deleted, FR-4.10/OQ-40).
  • No foreign keys at all, by design: audit_log_entries — see FR-7.1/OQ-25/NFR-AUD-1's append-only requirement; a real FK would force a wrong outcome on every hard delete (destroy the entry, block the delete, or mutate an immutable table). It's the one entity in this whole ERD drawn with no connecting lines at all — that isolation is the correct, confirmed shape, not a missing relationship.
  • Cascades transitively, confirmed intended: deleting a personal accounts row (user deletion or household departure) cascades to investment_holdings, which cascades to valuation_snapshots/investment_ schedule_entries/goal_allocations — even when the allocation fed a still-live shared Goal. The Goal survives; its live-derived progress (FR-8.8) simply recomputes from whatever Holdings remain.

What's deliberately not shown

  • The 5 parked Accessors (PortfolioAccessor, OpenBankingConnectionAccessor, OpenFinanceBrasilAccessor, USOpenBankingAccessor, MarketAnalysisProviderAccessor) — unlike the VBD/EBD diagrams, which draw parked components dashed-and-visible because their architectural role is already decided, these have no table design decided at all yet. There's nothing concrete to draw even as a placeholder; they're absent from this ERD entirely, not dashed.
  • Partial unique indexes and CHECK constraints (e.g. "exactly one Owner per household" on household_memberships; the scope-based partial unique index on budget_targets; percentage > 0 AND <= 100 (whole percent) on goal_allocations) — ER notation shows cardinality between tables, not intra-table constraints. All of these are spelled out in 02-data-model.md's per-domain Invariants sections.
  • Application-level invariants that cross tables but aren't expressible as any DB constraint (subcategory- belongs-to-category, the backdated-balance cascade, the FR-8.3 100%-allocation cap) — same reason, and same pointer to the prose doc.
